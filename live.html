      Intake check

      Every request is checked once when it arrives, before it is routed. This sends one request to the planner's own intake code. Admitted requests join the plan. Flagged requests are real but need manual handling, so they are kept and reported, never silently dropped. Rejected records cannot be placed or served at all. Click the map to place a point, or use an example. Available while the live server is on.

      Diesel factor scenarios

      The same 90 scenarios re-scored at another diesel factor. Tier-1 CO2-e is diesel kilometres times the factor, and electric trucks count 0 g per km. The plans were made at 1000 g per km and are not re-planned, so this is what the same routes would emit, not what a planner told another factor would choose. The factors are the project's driving scenarios: low 780 (ABS Survey of Motor Vehicle Use 2020, rigid trucks), central 1000 (an unsourced assumption), high 1140 (derived from NREL low-speed refuse-style cycle data) and stress 1300 (Argonne GREET, Class 8a refuse truck, includes stationary fuel).

      The contract
      
    
      The output follows the solution.json contract (version 1), which a run checks itself against with this JSON Schema before it counts as finished. Every submitted request appears in it with exactly one outcome: collected, outstanding, flagged or rejected at intake. These runs are descriptive, not pre-registered results.
